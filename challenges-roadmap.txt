Challenges Roadmap
==================

1. Names, Variables, and Resolution
-----------------------------------

1.1 Deduplicate global-name constants

Challenge:
The compiler adds a global variable's name to the constant table every time the
identifier is encountered. Repeated references to the same global therefore
create duplicate string constants. This wastes space and increases the chance
of exhausting the constant table.

Questions:
- How does deduplication affect compiler performance versus runtime performance?
- Is the additional compiler complexity and memory usage a worthwhile trade-off?

Possible approaches:
- Search for an existing value in Chunk.writeConstantAs(). A linear search may
  degrade as chunks approach the 65,535-constant limit, and deduplication may
  need to exclude ordinary op_constant values.
- Maintain a per-chunk hash table from global names to constant indexes. This
  improves lookup time at the cost of memory for every chunk.
- Store a constant index and compiler epoch on interned ObjectString values.
  The epoch would verify that the cached index belongs to the active chunk.
- Investigate whether the GC allocator's global-name interning can participate
  without coupling runtime global storage to compilation state.

1.2 Optimize global-variable lookup

Challenge:
Looking up a global variable by name in a hash table every time it is used is
slow, even with a good hash table. Find a more efficient representation without
changing language semantics.

Possible approaches:
- Direct array access using assigned global slots, similar to local variables.
- Inline caches with invalidation after table resize or compaction.
- Address-stable indirection through a global pool. Interned ObjectString
  addresses should remain stable during a run.

1.3 Optimize local-variable resolution

Challenge:
The fixed local array makes stack-slot calculation simple, but resolving a local
reference requires a linear scan through the array.

Possible approaches:
- Maintain a scope-aware name-to-slot index alongside the ordered local array.
- Measure whether an index improves realistic compilation workloads enough to
  justify its bookkeeping and memory cost.

1.4 Support const globals

Challenge:
The const modifier is enforced for locals but not globals. Global const support
likely requires symbol metadata independent of the runtime value table.

Considerations:
- A compiler symbol table may allow globals to be addressed by indexes instead
  of names.
- Mutable recursion and declarations that refer to themselves complicate when
  a global symbol becomes initialized and writable.

1.5 Handle local-slot exhaustion without panicking

Challenge:
addLocal() reports an error when all 256 local slots are occupied, but callers
can continue as though the local was added. The for-loop compiler currently
force-unwraps resolveLocal(), so a loop declared at the local limit can crash
the compiler instead of producing a normal parse error.

Possible approach:
- Make addLocal() return the allocated slot or a failure value.
- Stop emitting bytecode that depends on the local when allocation fails.
- Avoid force-unwrapping resolveLocal() on error-recovery paths.
- Add a regression test with 256 live locals followed by a loop declaration.


2. Control Flow and Loop Bytecode
---------------------------------

2.1 Explore combined jump-and-pop instructions

Challenge:
Conditionals and loops frequently emit a jump followed by one or more pop
instructions. Explore dedicated jump-and-pop operations.

Questions:
- Do combined instructions improve runtime performance or bytecode density?
- Which combinations occur frequently enough to justify additional opcodes?
- Does instruction fusion make compiler stack accounting harder to verify?

2.2 Validate pseudo-range bounds

Challenge:
Modern for loops use pseudo-range syntax, but bounds are ordinary runtime
expressions. The lower bound is evaluated once, while the upper bound is
re-evaluated before every iteration. Bounds should be validated without turning
ranges into first-class runtime values.

Possible approach:
- Add a non-consuming op_check_range_bound instruction.
- Emit it after evaluating the lower bound and after every evaluation of the
  dynamic upper bound.
- Require numeric, finite, integral bounds.
- Decide whether bounds remain restricted to non-negative u32 values or expand
  to the largest exactly representable integer supported by f64.
- Report a range-specific runtime error instead of relying on the generic
  comparison or addition errors.

2.3 Add loop-control compilation context

Challenge:
Break and continue need targets and stack cleanup that depend on the innermost
active loop. Nested scopes and nested loops must not leak or pop the wrong local
slots.

Possible approach:
- Track an enclosing loop context, its scope depth, its continue target, and a
  list of forward break and continue jumps.
- Before emitting either control-flow jump, emit cleanup for locals deeper than
  the loop scope without removing those locals from the compiler's metadata.
- When closures are supported, close captured locals instead of merely popping
  them.

2.4 Define continue behavior for desugared for loops

Challenge:
Continue must execute the for loop's automatic increment before checking the
upper bound again. Jumping directly to the condition would skip the increment
and could produce an infinite loop.

Possible approach:
- Emit continue as a forward jump while compiling the body.
- Patch pending continue jumps to the synthetic increment section once its
  offset is known.
- For while loops, continue can jump directly to the condition offset.
- Cover continue from nested blocks and nested loops.

2.5 Define break behavior and exit cleanup

Challenge:
The natural loop exit retains the false condition on the stack and then pops it.
A break executed from the body has no condition value on the stack. Sending both
paths to the same cleanup instruction would pop the loop indexer by mistake and
could make the following scope cleanup underflow the stack.

Possible approach:
- Patch the condition's false jump to an op_pop that removes the condition.
- Place the break target immediately after that condition pop and before
  endScope() emits cleanup for the loop indexer.
- Collect forward break jumps while compiling the body and patch them to this
  separate break target.
- Reject break outside a loop and ensure an inner break never targets an outer
  loop.
